# Profile: code - Software source code (desktop, web, services, tooling)

**Profile of** `specs/fleet-factory-kernel.md` r5. **Profile revision:** r9. **Status:** `BENCHED`. **Benches:** cloudvore, conjugal, salesforce-tools, adversarialllm, agent-bridge, adobe-ingester, airmypc (build lane), mlv-app (source and tooling), dng-auto-processor (code gates per kernel §6).
A profile defines what acceptance means in its domain. It never weakens a kernel clause (kernel §5). File evidence against it as `P:code <field>` lines in `adjudications/factory-kernel/<project>.md`.

| Field | Rule |
|---|---|
| Subject identity (K3) | git tree OID of the candidate commit as it will be delivered, after any merge with the delivery target; a key on a different subject identity does not transfer. Where the delivery target advances under a candidate between review and landing, a landing subject may instead declare, before review, a nonempty manifest of repository paths that includes every repository input the reviewed behaviour or acceptance checks depend on, with external inputs pinned in the declared environment; K3 combines the path-manifest digest followed by the blob digests in path order. Reviewed and delivered identities must match, the intervening range must touch no declared path, and acceptance checks must re-run green at the delivered tree. Receipts bind each key to that identity and record the reviewed and delivered commits and the shared stable patch-id, which corroborates identity and never substitutes for it. Register-permitted runtime subjects use a manifest listing register-relative target paths in path order, with full candidate and expected pre-state digests; K3 combines the ordered component digests. Prefixes are locators only. Generated binaries are identified by the build receipt's output digests; for code/design-review subjects, components are the subject blob OID, bench HEAD OID and rubric digest, in that order, combined by K3. Review contracts and terminal templates name each identity field's hashed artifact set and recomputation command; packet identity is distinguished from subject identity |
| Artifact store | git (shared checkout or worktrees); build outputs are not the subject. Register-permitted runtime subjects retain candidate, manifest and pre-state bytes with digests in the decision record's named evidence store, readable by an independent verifier |
| Determinism class | deterministic by default; flaky suites are declared per test, never silently retried |
| Acceptance evidence (K5) | the project's pinned acceptance checks for the declared artifact kind run at the exact subject identity and declared environment, including interpreter and TEMP/TMP where applicable (for example N identical green runs), executed or authenticated; replay agreement alone is not acceptance (Approach A Round F1, cluster C3). Before work, bind the acceptance contract by digest, including checks, harness limits, review scope, round budget and round-closing rule; the same contract judges every round. Out-of-contract findings open follow-ups unless they expose a binding-invariant breach. Bind durable acceptance receipts by content digest; log offsets are locators only. Documentation, doctrine and code/design-review subjects declare the rubric and required roles before work; acceptance requires their completion receipts and an independent acceptance decision bound to the exact subject |
| Independent key (K6) | a verifier from another model family (R3) whose class has not become a producer of the subject, a CI runner the producer does not control, or an attended human verifier other than the producer named by the register. Review-key charters declare execution or static review before dispatch. Execution charters require an execution-capable disposable environment; static keys authenticate required execution receipts by digest against the exact subject |
| Resource terminals (K5) | suite timeout, thermal admission, runner capacity, independent key unavailable: typed terminals, no partial green; retain the stopped candidate's bytes and receipts before rollback; parked work names its resume condition and the actor who can satisfy it. Owner-only resume conditions are sent through the register's escalation channel when the park is recorded; work not requiring the unavailable resource continues. Environment-only review blocks are typed terminals, not subject verdicts or completed rounds; retain attempts and expenditure |
| Delivery target (K7) | integration branch via the project's landing path; for feasibility subjects, the owner decision record; review branches push (R7). Register-permitted runtime installations assert pre-state digests, bank pre-state bytes, write candidates and record post-write digests as one recoverable transaction; rehearse reversal on a copy first. For git landings with a governing record commit, build the exact proposed record and run the validators and hooks that commit will face before any product push; refuse on failure. Contract validation covers every field downstream validators read, including evidence verdicts and next-packet executability. Stricter instance closure mechanisms and their budgets are declared before work |
| Human gates (K2) | releases, security-sensitive paths, frozen bytes, and anything the project's register lists; the register is reachable from every session checkout, classifies fleet-tool writes including permitted locations, names an owner-facing escalation channel, and takes precedence over bus prompts' procedural defaults |
| Budgets | wall time per suite, provider calls per subject; review rounds also report dispositions completed and subject changes, including zero, plus window counts of subjects accepted, delivered, parked and closed undelivered, with age and blocker for accepted-undelivered work; zero changes alone does not determine health |
| Claims (K3) | leases name the subject, owner, expiry and owned processes; where the instance releases claims by an observer's decision rather than by expiry, observer-released claims may replace leases and name the subject, owner, owned processes and the rule by which another observer decides them stale and releases. Either identifies the live holder rather than a short-lived claim-writing helper. A mutable checkout another project executes from is itself a claimed subject; same-host cleanup reads the claim before acting and never kills by command-line pattern alone. Read-only reviewer or adjudicator access requires enforced filesystem/process boundaries; a prompt or working directory is not enforcement. Otherwise treat the agent as mutation-capable, isolate canonical state from its tools, and name one scratch path. Audit canonical state before and after: HEAD, index entries and flags, refs, reflogs, stash, tracked contents, and ignored/untracked path inventories with content hashes; record every difference as a finding |
| Dispatch preflight (K9, K10) | the spending tool runs the project's resume gate before dispatch and retains its result, the inventory snapshot and digest, and account-parity evidence; the gate fails if the session's register digest differs from the current register. Inventory verification uses the launcher path dispatch uses; resume failures identify each losable item and its writer; failed or stale checkpoints name their last passing time and resume condition; launcher diagnostics are retained, and a CLI invocation failure is not evidence that a model is absent |
| Stress on the kernel | shared-checkout index races, worktree-scoped locks, and plumbing commits onto a checked-out branch (all three measured in Round F1); cross-project execution of a mutable tool checkout and pattern-based process kills on a shared host (airmypc, 2026-09-14) |
