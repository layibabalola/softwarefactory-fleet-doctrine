- **Soft (verified by CoS; NOT a Blocker): Codex Blocker 1, the late share-read reader at `:184`.**
  - **The mechanism is real.** `DeleteEntry` opens each entry with `DELETE | READ_ATTRIBUTES | WRITE_ATTRIBUTES` and share `SHARE_READ`, with no data access (`factory/cleanup-dependencies.ps1:184-185`).
  - Apply's recollected walk opens every entry with `READ_DATA` and share 0 (`:146-147`), so a reader already open at walk time is caught as in use.
  - But a reader that opens **after** that walk and before `DeleteEntry` reaches its file, with `FILE_SHARE_DELETE` (Node's default), can coexist with the delete handle. `MarkDeleted` (`:205-219`) then succeeds, and the file becomes delete-pending. The reader keeps its open data (legacy disposition), and the file disappears when the reader closes. The parent directory's disposition then fails, and the run ends `PARTIAL`.
  - The late-holder test `factory/cleanup-host.test.mjs:481` accepts `delete refused: pkg` (i.e. the file *was* marked) and only asserts that `pkg/` survives, although its title says "its file and directory survive".
  - **Why it's soft:**
    - A late arrival must *start* using a worktree that Apply has just proven clean, finished, owner-free and process/handle-free, while cleanup holds the global gate lease.
    - Codex's fix (an exclusive data-access open) only protects the one held file. Siblings already walked are gone either way, so it would turn this into `entry in use` without protecting a lane that starts mid-Apply.
    - The data is rebuildable.
  - Soft prefer: open files with `READ_DATA` and share 0 during delete, so that a late holder refuses before marking. Make `:481` assert that the held file's path and bytes survive. Soften the row's "never damage" stated-limit wording for this window.
  - *Surfaced by the Iverson advisory; verified by CoS.*
