## Blockers

- **Changing the Look Assist flavor in the GUI after Look Assist has applied removes the look instead of re-grading it** (Iverson Codex Blocker 1; CoS-reverified at tip `1ad30287`; `platform/qt/MainWindow.cpp` blob `4bb7063a` is byte-identical to prior tip `d5e05784`, so line refs hold). `on_comboBoxLookAssistFlavor_currentIndexChanged` (`:28078-28085`) stamps the new flavor on the receipt and calls `on_checkBoxLookAssistEnable_clicked(true)`.
  - **What happens:** that path immediately runs `restoreLookAssistBaseline` (`:28111`), which writes the pre-Look-Assist baseline into the receipt and sliders. It then calls `setReceipt` and defers the re-analysis to the next settled frame. When that frame arrives, the deferred callback returns at `look_assist.apply.dedup_skip` because `m_lookAssistAppliedReceipt == ACTIVE_RECEIPT` is still set from the previous apply (`:28162-28168`). The handler never clears it. Only the off path (`:28257-28258`), a dropped async result (`:16075-16077`) or the smoke reset (`:8306`) do.
  - **User-visible result:** switching Classic → Cinematic or back with Auto Look Assist on leaves the clip showing its **un-assisted baseline** while the checkbox still says on and the selector says the new flavor. That state is saved into the receipt (baseline sliders + new flavor). It stays wrong until the user toggles Look Assist off/on or something else clears the marker. It doesn't apply the *other* flavor's sliders; it applies none. This contradicts the docs ("Changing it re-runs Look Assist the way switching it on does", `docs/look-assist-flavors.md:71-72`).
  - **Fix:** clear `m_lookAssistAppliedReceipt` (and bump `m_lookAssistAsyncGeneration` so any pending worker is dropped) before re-entering the enable path. Add a behavioural test; the current pin is source-text only (`tests/console/test_look_assist_flavors.cpp:389`).
- **In the GUI, a receipt with a missing or unknown flavor takes the selector's flavor instead of Classic** (Iverson Codex Blocker 2 plus Claude Improvement 1; CoS-reverified at `1ad30287`). `setSliders` changes the selector only when `findData()` recognises the receipt value (`MainWindow.cpp:14927-14932`). `currentLookAssistFlavor()` then passes an **empty receipt layer** to `lookAssistSelectFlavor` (`:28066-28067`), so the GUI resolves env → selector and never reads the receipt's own value.
  - **Missing flavor:** this is the realistic trigger. The writer omits the element for Classic (`:14288-14290`), and the docs say "absent means Classic" (`docs/look-assist-flavors.md:69-70`). But a Classic clip opened while the selector is Cinematic (because the user chose it, or because an earlier Cinematic receipt switched the selector and `writeSettings` persisted that, `:11536`) is re-analysed Cinematic (`:14963-14974` and the deferred apply via `applyLookAssistToReceipt` → `currentLookAssistFlavor()`, `:15580`). `setReceipt` then stamps it `cinematic` (`:17259`), so the wrong grade persists into the saved session and into later headless batch output (`ReceiptApplier.cpp:519-520`).
  - **Unknown flavor:** a hand-edited or bogus value (e.g. `<lookAssistFlavor>bogus</…>`) leaves the selector untouched and silently gets its flavor with no `look_assist.flavor.unknown_value` warning. The docs require "An unknown value is **Classic**, never a fall through to a lower layer, and is logged" (`:75-77`). This is narrow (needs a hand-edited receipt); the missing-flavor case is the one users will hit.
  - **Never garbage:** the selector only ever yields Classic or Cinematic. The failure is the wrong (Cinematic) grade on a Classic clip, which is user-visible in any session mixing flavors. Headless is unaffected: it reads the receipt layer.
  - **Fix:** pass the active receipt's `lookAssistFlavor()` as the receipt layer in the GUI resolver, treat absent as Classic for a receipt that has already been Look-Assisted (baseline valid), and apply the unknown → Classic + warn rule before touching the selector. Add behavioural tests for absent / Classic / unknown receipts under a Cinematic selector.
