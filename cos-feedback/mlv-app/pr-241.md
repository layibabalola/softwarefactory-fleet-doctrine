- Soft, CoS-verified (Codex Blocker, Claude Improvement; **not** promoted): the exclusion hole is real and points **fail-open**, but in practice it is narrow. In `Get-PresentMonProcessSnapshot` (`tools/profiling/bachelor/playback-attr-3-cuda-job.ps1:1308-1348` at tip 20cbf394; was :1291-1331 at d02fe8b3), a `PresentMon*` process is **excluded** (not counted live, so the sweep runs) when (i) its pid is any registered `Win32_Service` ProcessId, with the service never name-checked, or (ii) its path is readable, it isn't the pinned name or path, and its name misses `^PresentMon([-_.]?(\d|x64|x86|console|capture|cli)|$)`. The wrong direction is "live capture treated as not live → sweep terminates its session". What actually limits the harm is that the sweep only ever targets sessions named exactly `PresentMon` or `MLVAttr3-*` (`AttrCudaArtifacts.psm1:2037`):
  - **Service arm:** the owner's Intel PresentMonService creates ETW sessions named `PMService` / `PMService_ETL` (upstream `GameTechDev/PresentMon`). Those names are never sweep targets, so exempting the service can't stop its capture on Bachelor.
  - **Harness captures:** every harness capture runs the pinned image (always live via `pinned_image_name`), and other pinned versions match the capture pattern. A concurrent or other-version harness job is never excluded.
  - **What's left:** a manually launched, oddly renamed console PresentMon (e.g. `PresentMon (1).exe`, `PresentMon-dev`) at a readable path, running with the default `PresentMon` session at the moment a job starts. The sweep would terminate that manual capture's session. That is data loss for an ad-hoc owner capture, not a killed factory process.
  
  Ask: either drop the readable-path exclusion (treat every non-service, non-pinned `PresentMon*` as live), or name-check the service (`Win32_Service.Name -eq 'PresentMonService'`), and add the regex boundary table plus an odd-name readable fixture.
