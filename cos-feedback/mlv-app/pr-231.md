## Blockers

- **A PresentMon wait failure whose counters derive the *other* backend still ends with no receipt (exit 2).** At tip `c078999f`:
  - **The guard misses it.** `Get-DvBackendNotDerivable` (`tools/profiling/dual-venue/DualVenueRunner.psm1:807-812`, called at `Invoke-VenueLeg.ps1:540-541`) returns a reason only when *no* backend can be derived, or when a cpu summary has no `backend` field. It never compares the derived backend with `$Backend`.
  - **The validator refuses it.** In production, `Test-DvReceiptValid` adds `BACKEND_MISMATCH` when the derived backend differs from the receipt's (`psm1:1053`), so the status is INVALID (`psm1:1118`). `Write-DvReceipt` then throws `DVE_RECEIPT_INVALID` for a FAIL that doesn't re-derive (`psm1:1378`), and `Complete-Receipt` turns that into `DVE_RECEIPT_WRITE_FAILED` with `exit 2` (`Invoke-VenueLeg.ps1:183-186`).
  - **How the job reaches it.** `PRESENTMON_UNAVAILABLE` is not a venue-condition token, so it resolves to FAIL (`psm1:1211`, default at `:1251`). The wait-failure branch (`tools/profiling/bachelor/playback-attr-3-cuda-job.ps1:2453` / `:2460`) runs *before* the cuda eligibility gate (`:2583`), `GPU_RECON_FRAMES_ZERO` (`:2637`) and `CPU_FALLBACK_DETECTED` (`:2651`). It now publishes the measured session's real counters (`gpuSummary` + `gpuFramesTotal`), and on a variant job `backend=$Backend` too (`:3277-3283`). Its token is not special-cased in `Get-DvDerivedBackend` (`psm1:787-798`), so plain counter rules apply. The result:
    - a cuda leg whose GPU reconstruction produced nothing (gpu 0, cpu > 0) derives `cpu`;
    - a cpu leg with gpu frames > 0 derives `cuda`.
  - **CoS executed the shared rule.** With the tip module imported in pwsh 7.4 on the box, the cuda shape (gpu 0 / cpu 478, `backend=cuda`) and the cpu shape (gpu 300, `backend=cpu`) each give `Get-DvDerivedBackend` = the other backend and `Get-DvBackendNotDerivable` = `$null`, so no INVALID rewrite happens. A matched control (gpu 478, cuda) derives `cuda`. The full `Write-DvReceipt` path was not executed; the rest of the chain above is from reading the tip code. `test_dve_leg_terminals.py` has no backend-mismatch case.
  - **Why it's realistic on Ultra-Magnus.** The PR body says both CUDA owner legs on UM hit the PresentMon wait failure, and "PresentMon does not exit within 35 s on UM" is out of scope here, so on UM today the wait-failure branch is the normal end of a cuda leg. Any cuda leg that falls back to CPU reconstruction, which is the product failure exit 13 / the eligibility gate exist to catch, is masked as `PRESENTMON_UNAVAILABLE` and then refused: no receipt. If #230 lands first, this branch gets rarer but stays reachable (PRESENTMON_TIMEOUT when the kill can't confirm exit; a nonzero rc after a failed terminate). How often a CPU fallback happens on UM: not checked by CoS.
  - **Unblock:** make the shared rule also return a typed reason when the derived backend (or the summary's own `backend` field) differs from `$Backend`, so the leg ends as a typed INVALID receipt that keeps its evidence. Better still, give `PRESENTMON_UNAVAILABLE` terminal-aware derivation the way `GPU_RECON_FRAMES_ZERO` has. Add production-path tests for both counter shapes (cuda gpu 0 / cpu > 0; cpu gpu > 0) that expect a written INVALID receipt, not exit 2.
  - *Surfaced by the Iverson advisory (Claude + Codex shared Blocker); verified by CoS.*
