## Improvements
- **New, dump tooling. The helpers bypass the `$Pub` publish-write boundary.** `Start-AttrCudaHeapDumpWatch` creates `$Pub\heapdump` with a raw `New-Item -ItemType Directory -Force` (`AttrCudaArtifacts.psm1:2618`). It writes `heap-dump-watcher.ps1` with raw `[IO.File]::WriteAllText` (`:2648`) and then executes it with `-ExecutionPolicy Bypass`. `Stop-` writes `heap-dump.json` the same way (`:2690`). The module's own header and its neighbouring code ("New-AttrCudaDirectory only (never a raw New-Item -Force) -- matches every other $Pub") say every publish write goes through `New-AttrCudaDirectory` / `Publish-AttrCuda*`. Route these through those helpers, or record a reviewed, explicit exception in the module header.
- **New, dump tooling. A failed capture looks like a clean one in `heap-dump.json`.** A leg can come back with `dumps=[]`, `watcherExited=true` and `reason=null` in four cases: COMPILE_FAILED (rc 5), ATTACH_FAILED (rc 2), DUMP_FAILED (rc 3), and a watcher that found no target after its deadline. Stop only sets `reason` when it has to kill the watcher (`:2677-2685`), and the start side disposes the Process object, so the exit code is lost. Record the watcher's rc, or parse `ATTACHED`/`*_FAILED`/`DEBUGGER_EXIT` into a `state` field. Then have the r3 driver treat "requested but not attached" as capture-missing, not as a clean stop cycle. Otherwise, if a crash goes uncaptured, the soak can't tell whether there was no crash or no debugger.
- **New, soak accounting. Don't pool debugger-attached legs with unattached ones.** The body already folds the r6b legs into the totals (CTL-W 0/17, FIX-W 1/19). An attached debugger changes conditions in two ways. First, while a process is being debugged, `SetUnhandledExceptionFilter` filters are not called, so CrashForensics' own minidump hook (`CrashForensics.cpp:582`) is silent on those legs. Second, every thread create, DLL load, first-chance exception and any OutputDebugString becomes a debugger round trip, which can shift race timing. Report the attached legs as their own rows, and note that a 0-crash attached run is weaker evidence than an unattached one.
- **New, dump analysis. Plan for "detector, not writer".** A first-chance c0000374 dump shows the heap call that *detected* the corruption, often a later free or alloc, plus the full heap. It usually won't show the write. Before the soak ends, say how the dump will be worked (`!heap -s -v`, block owner by vtable/allocation site, neighbouring-block analysis). Also name the follow-on if it only gives the detecting stack: a full page heap or ASan arm, the same detector gap as the r5 caveat below.
- **New, small.** Full-memory dumps of MLVApp may be several GB. The runner copies them (`Invoke-VenueLeg.ps1:555-560`) rather than moving them, and the evidence is hashed, so record `bytes` and the copy/hash time on the first real dump. Nit: test comments still say "procdump" (`test_dual_venue_evidence.py:5694`, `:6440`).
