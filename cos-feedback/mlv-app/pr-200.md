Claude calls it "residual / still open structurally" and says the damage is limited. CoS re-verified at `faaf2676` and found no path to a wrong-file delete or an escape:
  - **The race is real.** In the loop in `Remove-AttrCudaOwnerFootageRecordedLinks` (`:692-707`), `:693` re-proves the directory pin (volume serial + file id; the ancestor reparse check `:620-621` only runs for a relocated dir). Then `:698` reopens `Join-Path $Directory $record.Name` **by path** through `Remove-AttrCudaOwnerFootageLinkName`, which calls `CreateFileW` (`:652-653`). `FILE_FLAG_OPEN_REPARSE_POINT` only protects the last component, and no directory handle is held between the check and the open. So a directory or ancestor swapped for a junction in that window would be followed.
  - **The damage is bounded on the same handle before any delete:**
    - The object must not be a reparse point (`:658`) and not a directory (`:659`). It must have `NumberOfLinks >= 2` (`:660`), and its volume serial + 64-bit file index must equal the recorded identity (`:661-663`). That identity was recorded at link creation (`:767-773`), i.e. it is the owner clip's own file object.
    - The handle is opened without `FILE_SHARE_DELETE` (`:647`), so the link count can't drop before the delete at `:665`.
    - The leaf must be the neutral name `owner-clip.MLV` / `owner-clip.M<nn>` (`:295-298`).
    - So a redirected open can only remove **another name of the same clip file, spelled with the neutral name, while at least one other name survives**. No other file's bytes can be touched, nothing can be deleted outside that identity, and the job's own private link, which is never deleted in this case, keeps the bytes alive.
    - The owner's own name is only at risk if the consented clip is itself named `owner-clip.MLV` in the redirect target, which consent-table names such as `M16-1243` are not. The realistic target is a leftover neutral link from another job, which is disposable.
  - **Preconditions:** someone must swap a folder this job has just created, either the relocated `<clip drive>\mlvtmp\<JobId>-owner-clip` or (in today's production layout) `$Work\owner-clip` under `C:\mlvtmp`, or one of its ancestors, within the millisecond window between `:693` and `:698`. That needs write access as the non-elevated agent account on a single-owner host, and such an actor could already delete the clip directly. No privilege boundary is crossed, and no benign process swaps directories for junctions. This matches the CoS r1 judgement (soft).
  - **Soft prefer:** anchor the delete open to a held, identity-verified directory handle (e.g. `NtCreateFile` with `RootDirectory`, as the AdvLLM #186 cleanup adapter does), or hold the pinned directory handle without `FILE_SHARE_DELETE` from the check through the delete.
