# MLV-App #435 GPU-FIELD-TELEMETRY-EXIT-DEADLINE-1: bound the session-end flush (backend lock, EvtQuery, write)

**This is the follow-up fix for the #409 SHARED BLOCKER** (session end can hang the GUI thread on the backend mutex; see `cos-feedback/mlv-app/pr-409.md`). It takes the fix CoS proposed there: the getter is bounded with trylock and pinned by a runtime test that holds the mutex.

## Improvements
- `tests/pipeline/test_gpu_field_telemetry_capture.cpp:1265-1276` (Dot 5dfa97a8; CoS concurs): the runtime pin covers backend-lock contention only. Add a stalled-write / System-log case: inject a write or `EvtQuery` that blocks past the deadline, and assert `sessionEnd` returns within `kSessionEndWaitMs`. Measure that callback separately from complete-close success, because `appCloseForTesting` (`GpuFieldTelemetry.cpp:763`) joins the pool with no bound.
- New (CoS): the after-fault worker still calls `flushImpl("after_fault", true, true)` with `describe = true`, so it takes `reconDescribe()` (`:339`), the unbounded `llrpGpuPlaybackReconGetBackendInfo`, on the worker. If a stuck backend call holds the mutex while that worker is inside the describe step, `sessionEnd`'s `waitForDone(kSessionEndWaitMs)` (`:404-405`) times out and the session_end record is skipped. That is bounded, not a hang, and it matches the existing "leave State to it" design, but the record is lost exactly when a fault and a stuck call coincide. Consider using `llrpGpuPlaybackReconGetBackendInfoWithin` (or the cached model) on the worker too.
- Carried from #409, not addressed here: `recordFault` stamps delivery time instead of the DLL's captured `utc_ms`.

## Notes
