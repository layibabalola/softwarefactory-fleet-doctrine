1. Child-only mutation is supported by source. The new call is inside the Codex branch and changes `ProcessStartInfo.Environment`, not caller `$env:PATH`; Claude branch is untouched. The function reads only the configured MINGW_ROOT value plus the child's existing PATH. No credential read or network API is added. 2. Candidate gates prevent directly serializing relative paths, explicit UNC paths, semicolons, and quotes into added entries. Exact ordinal keys avoid culture-fold collisions; only drive-letter case is folded. Inspection confirms no filesystem lookup or thread/runspace in the helper. These are useful containment properties, not proof that a selected directory is trusted or locally backed.

3. PATH is broader than a two-DLL allowlist. Appending both configured and default toolchain bins makes every otherwise unresolved executable and PATH-searched DLL in those directories discoverable by the Codex child and inheriting descendants. Existing PATH entries retain their relative precedence; appended entries do not displace an earlier incompatible DLL or override application-directory/system loader precedence. This is an inherent design tradeoff, not a proven exploit. Document trusted-toolchain assumptions and regression-test existing executable resolution and incompatible earlier runtime scenarios in an authorized Windows validation setting. Source: https://github.com/SuperDimensionalSpaceFortress/MLV-App/blob/071338fa0ace74824763466b82e46cbc97fc149c/tools/coordination/Invoke-Lane.ps1#L1982-L1984 and #L2030-L2046 .

This is a residual limitation to characterize, not evidence this helper stalls. Do not restore blocking existence checks as a superficial remedy.
