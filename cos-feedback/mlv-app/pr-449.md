## Improvements

- **CoS catch: the docstring parser drops a whole test if a stamped line lands between its id and its result.** In `ci_unittest_shard_timings.class_seconds`, `pending` is cleared by any stamped line that isn't the result. A docstring test that logs one warning loses its entire runtime. CoS probe: head at 00:01, a `WARNING` line at 00:02, `Doc line ... ok` at 00:40; the class gets 1.0 s instead of about 39 s. That undercount is the same staleness this card fixes. Suggested fix: keep `pending` until the next `TEST_LINE` or `DOC_HEAD` match, and attribute the gap from the head stamp to the result stamp. Add a `TimingsTests` case with an intervening log line.
- **CoS catch: the ubuntu table has the same stale-coverage defect, and the new pin skips it.** `test_the_table_measures_nearly_every_discovered_test` loops over `("windows",)` only. On tip, the ubuntu table leaves 911 tests in 121 classes (22.3 %) unmeasured, past the 5 % bar the PR sets for windows. Ubuntu shards are not near their 30 min cap today (master run 38714437643: 10 / 6 / 8 min), so this isn't a blocker. Either re-derive the ubuntu table and add `"ubuntu"` to the loop, or write the exemption and its reason into the test.
- **Prevention (freshness of known rows).** The budget pin costs shards with the same table it checks, so it can't see drift in rows that already exist. That drift is half of this incident (`EvidenceBoundReceiptTests` 204 to 666 s, `LineEndingsCannotHideACommittedFileTests` 9.9 to 491 s). The PR body says this honestly. The gap is that no gate compares the table with real runs. Proposed check for the successor card: have each shard step print measured versus planned seconds, and warn (or fail on master pushes) when a shard's actual test time is over 1.5x planned. That would have flagged shard 2 at about 2.9x well before the cap.
- **Soft:** the 5 % unmeasured pin will eventually go RED on an unrelated PR that adds test classes. That's an acceptable forcing function. Consider naming the exact re-derive command, and the 6-run sample the table came from, in the failure message or a header comment in the JSON.
