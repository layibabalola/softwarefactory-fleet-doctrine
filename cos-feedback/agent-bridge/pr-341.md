## Remedy assessment

### Provenance and malformed/conflict boundary

https://github.com/layibabalola/agent-bridge/blob/9fe4c31a969632bc0886898893aab5a78713a9cb/agent_bridge/pack_cli.py#L143-L218

The reader requires a JSON object, exact integer schema 1 (not bool), requested pack ID, nonempty UTF-8-encodable project/version of at most 128 characters, and 64 lowercase hexadecimal SHA characters. It now additionally requires installed_at to parse as an offset-bearing datetime and installed_by to satisfy the same bounded-text predicate. Both checks precede already_installed and install_conflict. Missing/null/list/wrong-type provenance therefore rejects without returning stored field contents. Arbitrary extra keys are permitted by the explicit contract. installed_by is provenance text, not authenticated identity; another nonempty operator name is deliberately allowed. No role authority derives from it.

The timestamp check accepts datetime.fromisoformat's language rather than an exact round-trip spelling of utc_now: alternate accepted separators/forms and fractional precision are not canonicalized. It does not compare freshness or authenticate the time. This is acceptable for the stated offset-bearing-time purpose, not a security attestation. If strict ISO grammar or exact writer-format equality is intended, narrow the spec or add a lexical contract and cases; no MUST is established from the present parser tolerance.

Static witnesses: remove either provenance key from an otherwise matching seven-field record, or put installed_at=null/installed_by=[]; the new predicate rejects before identity success. A well-formed record whose version is 0.0.1-older still deliberately returns install_conflict and echoes the bounded version. The no-echo promise applies to malformed rejected records, not every stored record.

### Bounded regular-file read

https://github.com/layibabalola/agent-bridge/blob/9fe4c31a969632bc0886898893aab5a78713a9cb/core/storage.py#L727-L751
https://github.com/layibabalola/agent-bridge/blob/9fe4c31a969632bc0886898893aab5a78713a9cb/core/storage.py#L682-L714

The installer always supplies the fixed positive cap 65536. The helper opens once, fstats that same handle before reading, and returns at most the cap; a cap+1 read detects oversized input without loading the entire file. Checking descriptor type avoids a separate-stat type check being invalidated by a later pathname replacement. On POSIX, O_NONBLOCK prevents a FIFO open waiting for a writer, then S_ISREG rejects it without attempting a data read. Directory/device/socket cases either fail opening/wrapping or fail the descriptor check. On Windows the existing shared-read adapter retains READ/WRITE/DELETE sharing, binary mode and ownership cleanup. Existing storage functions are unchanged. Both normal and exceptional read/check paths close the handle; fdopen failure closes the raw POSIX descriptor.

The cap bounds requested returned data and memory order, not strict physical I/O: BufferedReader can prefetch a bounded buffer. It also is not a wall-clock timeout for regular-file I/O. Network filesystems are already unsupported by storage's stated model. O_NONBLOCK is not a universal deadline mechanism, nor protection against every exotic filesystem/device open. Those are platform/threat-model limitations, not evidence the local regular-file/FIFO fix is ineffective.

### Cooperative race semantics and refusal effects

https://github.com/layibabalola/agent-bridge/blob/9fe4c31a969632bc0886898893aab5a78713a9cb/agent_bridge/pack_cli.py#L107-L130
https://github.com/layibabalola/agent-bridge/blob/9fe4c31a969632bc0886898893aab5a78713a9cb/agent_bridge/pack_cli.py#L243-L306
https://github.com/layibabalola/agent-bridge/blob/9fe4c31a969632bc0886898893aab5a78713a9cb/agent_bridge/pack_cli.py#L309-L375

The special project-name rejection now occurs immediately after normalize_project, before catalog/runtime/roles checks. CON plus approval-desk therefore reaches project rejection, addressing the prior precedence mismatch.

Unlocked existing-record answers create no explicit directory/lock/data artifacts. Missing records progress to the same single per-record lock; path and existing-record checks rerun under that lock, and the atomic unlocked writer avoids nested lock acquisition. A cooperative atomic replacement leaves an opened reader on a stable old or new regular file. The helper itself does not add a lock or mutate state. OS access-time updates are not excluded by this read-only statement.

The old carve-outs remain: an under-lock rejection or contention can leave directories and lock artifacts; a failed write can retain a serialized temporary candidate. The module documents these K-a/K-b exceptions. The spec's blanket 'A refusal writes nothing' remains less precise than the module, but this is preexisting wording, not a new guarantee delivered by #341.

No hostile-local-tree isolation is added: the pathname containment check still precedes opening and does not pin parent directories. A noncooperating actor can replace directories/symlinks or alter a regular inode in place. S_ISREG does not prove containment or that bytes came from a single in-place version. That accepted cooperative-writer/trusted-local-tree boundary should remain explicit. No remote attack or role/authority escalation is established.

## Nonblocking observations

### SHOULD / reusable-helper hardening: reject invalid byte limits before opening

Location: https://github.com/layibabalola/agent-bridge/blob/9fe4c31a969632bc0886898893aab5a78713a9cb/core/storage.py#L727-L751

The newly public helper accepts max_bytes as int but never validates its range. Minimal static witness: calling read_bytes_cooperative_bounded(path, -2) computes handle.read(-1), Python's read-to-EOF request. It can load an entire large regular file before the later len(data) > -2 rejection. This violates the helper's apparent bounded-read guarantee for an invalid negative argument. It does not affect pack install, which always passes 65536, and is not a current input-controlled CLI vulnerability.

Remedy: validate a nonnegative integer cap before opening, or explicitly document the valid-argument precondition. Suggested regression cases: -2 and -1 reject before any open/read; zero accepts empty and rejects one-byte files; normal cap and cap+1 retain current behavior. All are proposed, not executed.

### SHOULD / test robustness: FIFO test needs an external deadline

Location: https://github.com/layibabalola/agent-bridge/blob/9fe4c31a969632bc0886898893aab5a78713a9cb/test_pack_install.py#L953-L964

The test calls install synchronously and only checks elapsed time after return. Minimal static regression witness: remove O_NONBLOCK from the reader; opening a FIFO with no writer then blocks before the installer reaches any lock. lock_timeout_seconds=5 does not govern that open, and the elapsed assertion is never reached. Thus the test named 'within the lock timeout' would hang rather than enforce its own five-second deadline. Current source includes O_NONBLOCK, so this is a test-quality issue, not a demonstrated current hang.

Remedy: run the FIFO scenario in a child with an external timeout and guaranteed cleanup, or provide an equivalent independent watchdog. Add supported POSIX execution when available. Windows-only CI success must not be represented as FIFO/POSIX execution coverage.

A minor evidence limitation in the direct-reader test: unlinking after the call does not prove handle closure when the Windows handle intentionally shares DELETE; a leaked share-delete handle can still permit unlink. Source with-block ownership is persuasive, but a direct close/descriptor assertion would independently pin that property.
