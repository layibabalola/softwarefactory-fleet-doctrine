## B1-PREFS-TOGGLE-FALSE-PERSISTENCE — medium

On the normal Auto-download watched changes toggle, Automations.cs:755–767 has no TaskName and changes only UserPrefs.WatchAutoDownload. If config.user.json saves but UserPrefs.TrySave fails, AutomationsForm.cs:921–933 reports “Automation settings were saved, but the window preferences could not be saved.” That misclassifies the automation choice itself as saved. UserPrefs.cs:819–872 confirms false denotes failed or refused prefs persistence. The value remains in memory; it is not yet persisted. Reload reconstructs from that memory and may replace the warning because operation feedback is retained only for failures.

This is an introduced false-success/feedback classification, not a newly introduced disk failure. The earlier UX audit noted missing retry guidance but described the failure as window-layout-only; it did not identify the automation-setting impact. A close-time save is attempted and a later save may succeed, so inevitable data loss is not claimed. The close Save wrapper discards TrySave's result.

**Remedy:** Either restore captured state, or clearly retain “active in memory, not saved” and offer a non-flipping retry. Do not advise toggling again, which reverses intent. Inject config success and prefs failure for watch-auto-download and another prefs-backed automation; assert disk unchanged, truthful feedback retained across Reload, chosen rollback/session-only behavior and successful non-flipping retry. Include close-save failure and a config-backed control.
