## Blockers

**Addressed on c84c11b0:** the stale "source: GitHub Actions" anchor wording (raised on 41a1ef6e) is fixed. `review-keys-required-status-r1.md` last checkbox now pins the required check to the verifier App id or the ruleset workflow path and ref, and says never to pin it to the plain Actions app; `review-key-publication-r1.md:37` matches.

1. **"Runs queue and never cancel each other" is false on GitHub, which reopens the delete-before-first-run race.** `docs/review-key-publication.md:95` relies on `cancel-in-progress: false`. GitHub's concurrency doc says that by default (`queue: single`) at most one run can be pending per group, and "any existing pending job or workflow in the same concurrency group will be canceled and the new queued job or workflow will take its place." Attack: post r2 CHANGES_REQUESTED, delete it while a run is in progress, then post any two comments. The pending `issue_comment.deleted` run is cancelled, its payload is lost, no later run can see the deleted comment, and r1 APPROVE counts again. Separately, :104 reads the mark back only from the **newest** anchor run, so two runs that overlap can drop each other's `deleted` entries, and :96's "monotonic" holds only within a single run.
   **Unblock:** (a) set `queue: max` on the group, and put `deleted` events in their own group keyed by comment id, so a deletion run is never pending-cancelled; (b) build the read-back as the **union over every anchor check run on every head of the PR** (max round per seat, union of `deleted`), not just the newest; (c) as a residual backstop, have the CoS spot-check compare each seat's ledger round count with its visible chain; (d) add dry-run cases: "delete r2, then post 2 unrelated comments within seconds" and "two runs overlap, each recording a different deletion".

2. **The ruleset alternative isn't implementable as written for most consumers.** "Require workflows to pass before merging" is an **organization** ruleset rule. GitHub's repository-level rules list has no such rule, so personal-account hubs (every `layibabalola/*` consumer) can't use it today; only org repos such as `SuperDimensionalSpaceFortress/MLV-App` can. Also, a Checks API run that a required workflow posts with `GITHUB_TOKEN` is still authored by the GitHub Actions app. So ":129 pinned to the ruleset's required workflow" has to mean the required-workflow rule itself gates the merge, and the doc must say how an `issue_comment`-driven recompute updates that gate (required workflows are triggered by PR events).
   **Unblock:** say the alternative is org-only and spell out what protection requires in that mode, plus how comment-driven recomputes update it. For personal-account repos, the App is the only anchor. Add a checklist branch: "personal repo, so App required".
