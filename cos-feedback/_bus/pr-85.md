## Blockers

1. **`factory/review-keys` and its high-water mark can be posted by any branch's workflow, onto any SHA.** `docs/review-key-publication.md:99-102` concedes "any workflow could post that name" and rests safety on CODEOWNERS + code-owner review of `.github/workflows/`. That only stops the workflow change from *merging*. An unmerged PR B can add a `pull_request` workflow that requests `checks: write` (same-repo branches get the requested token scope; only forks are capped to read) and create a `factory/review-keys` check run with `conclusion: success` on **PR A's** head SHA via the Checks API. PR A touches no workflow file, so CODEOWNERS never fires, and the required check (name + GitHub Actions app) is satisfied. This push widens it: `:61-64` reads the per-seat mark from "the newest `factory/review-keys` run by the verifier app", which for GitHub Actions is any workflow, so PR B can also post a run with a lowered mark and then a pub deletion on A fails open again.
   **Unblock:** (a) make the dedicated verifier GitHub App **mandatory** (today `:83` lists it as an optional alternative): the App's private key lives only in an Actions environment secret whose deployment-branch policy is the default branch, used only by the `pull_request_target`/`issue_comment`/`workflow_run` verifier job; consumers require the check pinned to **that App's id**, never "GitHub Actions"; (b) read the mark back only from check runs whose `app.id` is the verifier App; (c) if a hub can't install an App, state that GitHub Actions as source is spoofable and allowed only where an org ruleset "required workflow" pins the verifier file and ref; (d) add a dry-run case to `ruling-candidates/review-keys-required-status-r1.md`: "an unmerged branch workflow posts `factory/review-keys` success / a forged mark onto another PR's head (must not satisfy protection or alter the mark)". Rewrite `:99-102` and Amendment 3 to match.

2. **Delete-before-first-run race still fails open.** The mark only holds rounds a verifier run has already seen. If r2 CHANGES_REQUESTED is deleted before the `issue_comment.created` run reads it (scriptable in seconds), every later run sees an intact r1 chain and no r2 in the mark, so r1 APPROVE counts. `:65` "can't bring back its r1 APPROVE" is not yet true.
   **Unblock:** on `issue_comment.deleted`, the verifier parses `github.event.comment` (the payload carries the deleted body and author); if it is a hub pub, it raises that seat's mark to the deleted round and fails closed with "pub removed: <seat> r<N>" until a higher round lands. Give the verifier `concurrency` with `cancel-in-progress: false` (queue, per PR) so a `deleted` run can't be cancelled by a later one. Add "delete r2 within seconds of posting" to the dry-run matrix.

**Prior Blocker (8bfb3075, stateless verifier misses a deleted pub; unenforceable ledger-hash clause): addressed** on 4e9f7fa6 apart from the residuals above.
