# Three-stream parity and neutral quiescence — ruling candidate R1

**Status:** CANDIDATE / ZERO AUTHORITY.
**Measuring project:** Conjugal.AI.

This candidate is data for review alongside fleet proposals
[#30](https://github.com/layibabalola/softwarefactory-fleet-doctrine/pull/30)
and
[#31](https://github.com/layibabalola/softwarefactory-fleet-doctrine/pull/31).
It activates no scheduler or provider, grants no route or key, and claims no
project or fleet adoption. Those proposals already cover the general bounded
improvement loop; this candidate contributes non-duplicative controls measured
in Conjugal.

## Independently advance three workstreams

An adopting project reduces **FACTORY**, **PRODUCT**, and
**PROVIDER/OPERATIONS** separately on every controller wake. Each stream has
exactly one current disposition:

- `ADVANCE-NOW`: one named safe authority-correct action is executable now;
- `WAITING`: an exact serialized dependency or live writer must end naturally;
  or
- `OWNER-BOUNDARY`: progress requires authority that no current durable contract
  supplies.

For each stream the controller asks: **What safe authority-correct action can
improve this stream before the next wake?** A provider fence cannot suppress
product-local tooling or factory work; a factory writer cannot suppress
path-disjoint provider observation; and a product blocker cannot manufacture a
provider probe. If the same blocker survives two wakes or 60 minutes and a
local authorized correction exists, the controller executes or routes that
correction instead of restating the blocker. It performs at most one mutation
per protected surface, then re-derives all three streams from canonical bytes.

This is a coordination controller, not a fourth delivery lane. It retains one
integration authority and does not acquire implementation, review, verification,
landing, publication, provider, credential, or release keys. Existing route,
claimant, task, lane, and provider-native identities remain singular. An
unchanged fingerprint produces no mutation and no progress notification.

## Treat a live Git writer as serialization

An existing canonical `.git/index.lock` with a proved live or ambiguous writer
is `WAITING`, not route success and not a terminal route red by itself. The
controller preserves the exact claim and first-red evidence, performs only
disjoint read-only work, and never deletes, moves, bypasses, kills, duplicates,
or abandons the writer. When that writer ends naturally, continuation requires:

1. `index.lock` absent;
2. staging empty;
3. governing locks absent;
4. unchanged claimed subject and HEAD ancestry; and
5. no competing writer.

Only then may the exact existing task resume once by pointer. A possible orphan
is quarantinable only through a reviewed project mechanism after a stable file
identity/hash/time sample, no repository-associated Git process, no matching
handle, the project's minimum age, and a retained quarantine receipt. Age or
zero length alone never proves orphanhood.

Read-only Git observations establish optional-lock suppression before Git
starts. Factory mutations still use the project's single-writer
compare-and-swap mechanism; optional-lock suppression is never a real-lock
bypass.

## Neutral stable-absence evidence

Conjugal measured a process-quiescence observer that counted its own command
because the searched marker appeared in the observer's command line. A later
marker-neutral observation returned zero. The original red remains first-red;
the follow-up does not retroactively make the transaction green.

A portable stable-absence guard therefore separates observation from the thing
observed:

- watched values are content-addressed and loaded only after the sampler starts;
- self and observer ancestry cannot satisfy an exact-candidate predicate;
- raw command lines are not retained as evidence;
- path, owner, ancestry, or candidate ambiguity fails closed;
- unreadable candidate-capable processes are `UNKNOWN_PRESENT`, never absent;
- process-start and lock-event monitors are armed before the bounded window;
- three stable repository/process snapshots are required; and
- any transient canonical lock, unresolved start, monitor error, predicate
  drift, runtime contamination, or short window makes the receipt non-green.

The first Conjugal implementation candidate compiled and its provider-free
fake-evidence suite passed 19 hostile scenarios. Independent static review then
returned `CHANGES-REQUESTED` with six findings: watched-input pinning,
typed/exact candidate binding, PID creation identity and reuse, monitor startup
and loss, live precondition binding, and runtime-path coverage. No live stable
window or provider credit exists. These adverse findings are preserved as
requirements for a later forward correction, not hidden by the synthetic green.

## Portable negative controls requested

A fleet ruling should require adopting projects to prove at least:

1. blocking one stream does not suppress an authorized path-disjoint action in
   either other stream;
2. repeated blockage never becomes authority, while a newly satisfiable gate
   selects one bounded action on the next evaluation;
3. a live writer is preserved and resumed exactly once after quiescence;
4. an ambiguous or young lock cannot enter orphan quarantine;
5. an observer containing its own searched marker cannot prove presence;
6. an unreadable candidate-capable process cannot prove absence;
7. a transient lock between snapshots is detected by continuous event evidence;
8. three stable snapshots with an unarmed or incomplete event monitor remain
   non-green; and
9. unchanged authoritative state performs no write and emits no false progress.

Project-local cadences, paths, task names, provider/model names, lock ages,
schemas, commits, and route identifiers do not travel. Siblings adopt only
through local authority, reviewed implementation, exact negative controls, and
a durable `ADOPT(reference)` or `DISTINGUISH(reason)` disposition.
